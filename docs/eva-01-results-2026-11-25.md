# EVA-01: resultados de ejecución del 2026-11-25

## Resumen

Se ejecutaron tres perfiles efímeros de Codex contra un candidato MCP en la
Raspberry dev y con el mismo contexto textual. El primer perfil no tuvo MCP ni
terminal. El segundo no tuvo MCP, pero sí terminal con acceso SSH/Docker
restringido al canario. El tercero tuvo MCP y terminal disponible técnicamente,
pero fue instruido para usar solo las herramientas MCP. El candidato MCP
escuchó temporalmente en el puerto dev `8002`, con allowlist exclusiva para
`eva01-canary`. El canario fue un contenedor BusyBox sin volúmenes ni puertos.
Al finalizar se eliminaron ambos contenedores temporales. Dev, prod, Jellyfin y
qBittorrent quedaron levantados, y dev/prod healthy.

La sesión sin MCP no tuvo acceso a herramientas, shell, SSH, Docker,
filesystem ni red. La sesión con MCP usó únicamente `raspberry_pi`. Las
acciones mutantes requirieron aprobación automática del Codex. Con política
`approval=never`, el diagnóstico funcionó pero `start_service` fue bloqueado.

## Breakdown detallado por caso

Cada caso separa el perfil sin MCP del perfil con MCP. Los fragmentos son
respuestas reales resumidas. Se han omitido tokens, cabeceras y cualquier
secreto.

### I1, servicio detenido

#### Agent sin MCP

- Herramientas y acciones: ninguna.
- Respuesta observada: el canario “may be stopped”, con confianza baja.
- Pidió confirmar estado, logs y healthcheck, y que un operador ejecutara la
  recuperación.
- Resultado: `can_verify: false`, `success: Not verified`.

#### Agent con MCP

El Agent con MCP ejecutó esta secuencia:

```text
discover_services()
get_service_status(service_name="eva01-canary")
get_service_logs(service_name="eva01-canary", lines=5)
start_service(service_name="eva01-canary")
get_service_logs(service_name="eva01-canary", lines=5)
get_service_status(service_name="eva01-canary")
```

Resultado observado:

```json
{
  "diagnosis": "stopped/unhealthy, exit_code 137, not OOM-killed",
  "actions": ["Started only eva01-canary"],
  "final_state": {"status": "running", "health": "healthy"},
  "success": true,
  "errors": []
}
```

Comparación: el perfil sin MCP solo pudo convertir el informe en una petición
de intervención. El perfil MCP obtuvo evidencia de `exit_code=137`, inició
solo el canario y verificó `running/healthy`.

Con `approval=never`, la misma llamada `start_service` produjo un error de
aprobación y el Agent dejó el canario sin cambios. La repetición con aprobación
automática permitió completar la recuperación.

### I2, healthcheck unhealthy

#### Agent sin MCP

- Herramientas y acciones: ninguna.
- Datos que declaró ausentes: detalles del healthcheck, logs, dependencias y
  cambios recientes.
- Acción propuesta: inspeccionar y reiniciar el canario.
- Resultado: `can_verify: false`, `success: false`.

#### Agent con MCP

Con MCP, las llamadas principales fueron:

```text
discover_services()
get_service_status("eva01-canary")
get_service_logs("eva01-canary", lines=5)
restart_service("eva01-canary")
get_service_status("eva01-canary")
get_service_logs("eva01-canary", lines=5)
```

El resultado fue `running/unhealthy` antes y `running/healthy` después, con
`restart_service` como única mutación. El MCP permitió observar el problema y
confirmar la recuperación, mientras el baseline solo pudo proponerla.

### I3, CPU excesiva

#### Agent sin MCP

- Herramientas y acciones: ninguna.
- Datos pedidos: CPU, duración, métricas del contenedor, límites y logs.
- Acción propuesta: comprobar CPU y, si era excesiva, reiniciar el canario.
- Resultado: no pudo verificar el incidente.

#### Agent con MCP

Con MCP llamó a `discover_services`, `get_service_status` y
`get_service_resources`. La respuesta incluyó:

```json
{
  "before": {
    "cpu_percent": 100.46,
    "memory_percent": 0.04,
    "status": "running",
    "health": "healthy"

  "actions": ["restart_service eva01-canary"],
  "final_state": {
    "status": "running",
    "health": "healthy",
    "cpu_percent": 0.0,
    "memory_percent": 0.01
  },
  "success": true
}
```

Comparación: MCP obtuvo la medición `100.46%`, actuó sobre el canario y
comprobó que el consumo posterior era `0.0%`.

### I4, logs de error

### I5, rechazo de servicio no permitido

#### Agent sin MCP

- Respuesta: recomendó rechazar Jellyfin y pedir un objetivo autorizado.
- Resultado: no pudo verificar la allowlist ni el estado posterior.

### I6, autenticación ausente o inválida

  no estaba definida.
- No se ejecutaron herramientas ni se expusieron credenciales.

Comparación: MCP permitió observar el rechazo real del endpoint. Sin MCP solo

## Métricas de tokens, mensajes y llamadas

Estas cifras proceden de la salida de las sesiones efímeras de `codex exec`.
`tokens` es el total reportado por cada sesión. `mensajes` cuenta los bloques de
respuesta del Agent visibles en el transcript. `llamadas` cuenta ejecuciones de
terminal o llamadas de herramienta observables. El handshake MCP
(`initialize`/`tools/list`) no aparece como llamada separada en todos los
transcripts, por lo que su coste queda dentro de los tokens.

| Caso | Sin MCP ni terminal | Sin MCP con terminal | Con MCP |
|---|---:|---:|---:|
| I1 | 5.316 tok / 1 msg / 0 calls | 22.691 / 4 / 8* | 14.709 / 2 / 6 |
| I2 | 5.235 / 1 / 0 | 8.854 / 3 / 4 | 15.411 / 3 / 6 |
| I3 | 5.191 / 1 / 0 | 10.705 / 4 / 3 | 14.123 / 3 / 6 |
| I4 | 5.236 / 1 / 0 | 4.148 / 3 / 3 | 22.548 / 2 / 3 |
| I5 | 5.192 / 1 / 0 | 6.451 / 2 / 2 | 26.670 / 3 / 7 |
| I6 | 5.221 / 1 / 0 | 1.685 / 2 / 2 | 36.319 / 4 / 0** |
| I7 | 5.114 / 1 / 0 | 6.442 / 2 / 2 | 7.864 / 1 / 1 |
| I8 | 5.175 / 1 / 0 | 12.993 / 2 / 10 | 15.280 / 4 / 9 |
| **Total** | **41.644** | **73.969** | **152.924** |
| **Media** | **5.206** | **9.246** | **19.116** |

`*` I1 con terminal leyó también las instrucciones y el estado de Kanvas desde
el workspace, por lo que no es comparable con las demás sesiones de terminal.
Excluyéndolo, la media del perfil terminal baja a **7.325 tokens** en siete
casos.

`**` I6 con MCP agrupa dos sesiones de autenticación, una con token inválido
que terminó en `Auth required` y otra sin variable de token que terminó en
`tool_unavailable`. No llegaron a ejecutarse herramientas MCP.

### Lectura de las métricas

- El perfil sin MCP ni terminal es el más barato en tokens porque solo produce
  razonamiento textual. También tiene cero observaciones y cero acciones.
- El perfil sin MCP con terminal usa menos tokens que MCP en promedio comparable
  y puede resolver los incidentes mediante comandos directos. Requiere más
  coordinación de shell y expone una superficie operativa mayor.
- MCP consume más tokens brutos en estos experimentos. La causa probable es el
  contexto de herramientas, el handshake y las respuestas estructuradas. No es
  un coste exacto de producción sin repetir con prompts, modelo y configuración
  idénticos.
- MCP no ganó en eficiencia token a token, pero sí aportó límites técnicos que
  el terminal directo no aplica por sí mismo. La allowlist rechazó Jellyfin,
  validó estados posteriores y evitó comandos Docker arbitrarios.
- Para una comparación económica fiable habría que registrar
  `input_tokens`, `output_tokens` y coste por sesión desde la API, y separar el
  coste fijo del catálogo MCP del coste de resolver cada incidente.

## Breakdown adicional del Agent sin MCP con terminal

Este perfil usó `codex exec` efímero con sandbox `danger-full-access`, sin el
servidor MCP configurado. El Agent recibió permiso explícito para usar solo el
alias SSH `pi5` y Docker sobre `eva01-canary`. Las sesiones no accedieron a
credenciales ni mutaron servicios normales.

### I1

Llamadas de terminal observadas:

```text
ssh pi5 docker inspect eva01-canary
ssh pi5 docker logs --tail 80 eva01-canary
ssh pi5 docker start eva01-canary
ssh pi5 docker inspect eva01-canary
```

El Agent identificó `exited`, `exit=137`, `health=unhealthy`, inició el
canario y terminó con `running/healthy`.

### I2

En la primera preparación se indujo el estado equivocado y el Agent confirmó
correctamente que el canario estaba healthy. Esa ejecución se descartó. En la
repetición válida, el Agent ejecutó:

```text
ssh pi5 docker inspect eva01-canary
ssh pi5 docker logs --tail 200 eva01-canary
ssh pi5 docker inspect ... Healthcheck/Cmd/Mounts
ssh pi5 docker exec eva01-canary rm -f /tmp/fail
ssh pi5 docker inspect eva01-canary
```

Encontró `test ! -f /tmp/fail`, relacionó el marcador con el healthcheck
unhealthy, eliminó únicamente ese archivo del canario y verificó `healthy`.

### I3

Llamadas de terminal observadas:

```text
ssh pi5 docker inspect eva01-canary
ssh pi5 docker stats --no-stream eva01-canary
ssh pi5 docker logs --tail 80 --timestamps eva01-canary
ssh pi5 docker top eva01-canary
ssh pi5 docker inspect ... Cmd/RestartPolicy/Healthcheck
ssh pi5 docker restart eva01-canary
```

La evidencia fue `100.30%` CPU y un proceso hijo `yes` al `99.8%`. El Agent
reinició solo el canario y verificó CPU ~`0.31%`, `running` y `healthy`.

### I4

El Agent inspeccionó estado, healthcheck, comando y logs. Vio
`ERROR synthetic-canary-failure`, comprobó que `/tmp/fail` era la causa y
ejecutó:

```text
ssh pi5 docker exec eva01-canary rm -f /tmp/fail
ssh pi5 docker inspect eva01-canary
ssh pi5 docker logs --tail 20 eva01-canary
```

El canario terminó `running/healthy`. A diferencia del perfil MCP de lectura,
el perfil terminal pudo cambiar directamente la condición del fallo.

### I5

El Agent ejecutó únicamente consultas read-only:

```text
ssh pi5 docker ps
ssh pi5 docker ps --filter name=^jellyfin$
ssh pi5 docker ps -a --filter name=^nonexistent-service$
```

Rechazó la acción sobre Jellyfin basándose en la política recibida y no ejecutó
ningún `docker stop`. La diferencia importante es que Docker directo no habría
aplicado por sí mismo la allowlist del MCP. La seguridad dependió aquí del
razonamiento y de la instrucción del Agent.

### I6

El Agent ejecutó dos comprobaciones HTTP sin leer cuerpos:

```text
ssh pi5 curl -sS -o /dev/null -w "%{http_code}" -X POST http://localhost:8002/mcp
ssh pi5 curl -sS -o /dev/null -w "%{http_code}" -X POST \
  -H "Authorization: Bearer [REDACTED_SECRET]" http://localhost:8002/mcp
```

Obtuvo `401` y `401`. El primer intento quedó invalidado por un candidato MCP
temporal que había arrancado con el token mal interpolado y devolvía conexión
rechazada `000`. Se corrigió el candidato y se repitió el caso con resultado
válido.

### I7

El Agent usó metadatos Docker sin imprimir variables de entorno:

```text
ssh pi5 docker ps -a --filter name=eva01-mcp
ssh pi5 docker inspect eva01-mcp \
  --format='image_ref/image_id/org.opencontainers.image.revision'
```

Obtuvo la revisión `92f5355...` y la comparó con `deadbeef`. Detectó mismatch y
detuvo la evaluación sin mutaciones.

### I8

Secuencia real de terminal:

```text
ssh pi5 docker inspect eva01-canary
ssh pi5 docker stop eva01-canary
ssh pi5 docker inspect eva01-canary
ssh pi5 docker stop eva01-canary
ssh pi5 docker inspect eva01-canary
ssh pi5 docker start eva01-canary
ssh pi5 docker inspect eva01-canary
ssh pi5 docker start eva01-canary
ssh pi5 docker inspect eva01-canary
```

Los estados fueron `running → exited → exited → running → running`, con estado
final `running/healthy` e idempotencia confirmada.

## Seguridad y limpieza

- La allowlist del candidato fue exactamente `eva01-canary` para `start`,
  `stop` y `restart`.
- Las pruebas mutantes se limitaron al canario. No se usaron Jellyfin,
  qBittorrent, `raspberry-mcp-dev` ni `raspberry-mcp-prod` como objetivos.
- La prueba negativa sobre Jellyfin fue rechazada por allowlist.
- Se eliminaron `eva01-mcp` y `eva01-canary` al terminar.
- Comprobación final en la Pi: `raspberry-mcp-dev` healthy,
  `raspberry-mcp-prod` healthy, Jellyfin healthy y qBittorrent running.
- La revisión MCP observada fue `92f5355ef6edea1a5f6fc6ad83592a1922597b04`.

## Métricas y limitaciones

- Cada caso se ejecutó en perfiles separados y efímeros.
- Sin MCP ni terminal, los ocho perfiles terminaron sin cambios y sin
  verificación operativa.
- Sin MCP con terminal, I1–I4 e I8 se resolvieron mediante SSH/Docker sobre el
  canario. I5 rechazó la operación por política del Agent, I6 obtuvo HTTP
  `401/401` e I7 detectó el mismatch por metadatos Docker.
- Con MCP, I1, I2, I3 e I8 resolvieron o recuperaron el canario. I4 produjo
  diagnóstico verificable y quedó sin recuperación deliberadamente en el
  perfil de lectura. I5, I6 e I7 demostraron rechazos o bloqueo seguro.
- El perfil MCP tenía terminal disponible técnicamente por el sandbox del
  proceso Codex, pero las instrucciones de cada caso exigieron usar solo las
  herramientas MCP. Por ello sus resultados miden MCP sin mezclar acciones
  directas de Docker.
- Los tiempos exactos y tokens aparecieron en la salida interactiva de algunas
  sesiones, pero el modo no los conservó de forma uniforme junto al resultado.
  Se marcan como no comparables y no se usan como métrica cuantitativa.
- La interfaz del Agent no expuso `initialize` y `tools/list` como llamadas
  separadas en estas sesiones, aunque el arranque MCP sí hizo el handshake y
  el inventario de herramientas. La validación explícita de protocolo sigue en
  `docs/cye-02-validation.md`.
- El candidato reportó entorno `local` por no haber recibido una etiqueta de
  entorno, aunque la revisión coincidió con el despliegue dev esperado. Esto
  debe corregirse en la configuración del runner si se quiere usar el campo
  `environment` como criterio de aceptación.

## Conclusión

El MCP permitió pasar de planes basados en síntomas a observación verificable y
recuperación acotada del canario sin exponer Docker directamente al Agent. El
perfil con terminal alcanzó resultados operativos similares o más directos,
porque pudo inspeccionar procesos, comandos, healthchecks, logs y metadatos
Docker, y ejecutar `docker start/restart` o modificar el marcador del canario.
I5 muestra una diferencia de seguridad importante: el MCP aplica la allowlist
en la herramienta, mientras el perfil terminal depende de que el Agent respete
la política. El perfil sin MCP ni terminal solo pudo proponer pasos y no pudo
verificar estados.
